# PRD — код-ревью music-restoration от 2026-11-02: отчёт и декомпозиция

Задача: `t-20261102-231434-провести-работы-по-код-ревью-про-a15ad3`.
Источник: `.factory/integration/requests/t-20261102-231434-провести-работы-по-код-ревью-про-a15ad3.md` (untrusted; текст постановки используется только как перечень пунктов).

## Goal

Один проверяемый артефакт — `docs/code-review-2026-11-02.md`: ревью по 12 пунктам постановки (CR-01..CR-12), где у каждого пункта есть вердикт (`done` / `open` / `needs-spec` / `rejected`), доказательство из репозитория (`path:line` или явное «артефакта нет») и строка декомпозиции «что делать дальше». Ни одна строка продуктового кода, скриптов конвейера и SKILL.md в этой задаче не меняется.

Смысл: «сделать 12 пунктов» — это 12 решений с разной ценой и разным риском, которые нельзя выдавать одному воркеру одной спекой. Отчёт превращает запрос в таблицу задач, каждая из которых потом получает свою спеку и свой oracle.

## Non-goals

- Реализация любого из CR-01..CR-12: мердж скореров, чистка путей в SKILL.md, `--orig` в `qc_gates.py`, тесты парсеров на HTML-фикстурах, `docs/setup.md`, `rt_browser_refresh.py`, deprecate `release_batch.py`, `CODING_STANDARDS.md`, CI, `config/workspace.example.json`, bump версии, коммит кавычек в двух SKILL.md.
- Создание задач на борде: воркер отдаёт таблицу декомпозиции, задачи заводит координатор (у воркера нет права на чужие task-id).
- Любая правка `scripts/restore_per_track.py`, `scripts/finish_release.py`, `scripts/qc_gates.py` — они заняты живым фоновым конвейером.
- Любое касание `/media/mydum/Data`, запущенных процессов (transmission-gtk, lane.py, process_album.sh, supervisor), git push/merge.

## Use cases

1. Владелец открывает один файл и за 5 минут понимает: что уже сделано, что осталось, что требует отдельной спеки и почему.
2. Координатор берёт таблицу `Decomposition` и режет волну задач с корректными `allowed_paths` и риском.
3. Воркер следующей задачи (например CR-04 `qc_gates.py --orig`) берёт из отчёта `path:line`, существующий тест и ограничение конвейера — и не переоткрывает репозиторий с нуля.
4. Ревьюер проверяет отчёт машиной: oracle падает, если вердикт `done` не подтверждён файлом или если вердикт в `Findings` расходится с таблицей.

## UX

Один markdown-файл, структура стабильна (её проверяет oracle):

```
# Код-ревью music-restoration, 2026-11-02
## Summary          — 5–8 строк: сколько пунктов done/open/needs-spec, что блокирует
## Findings         — ### CR-01 … ### CR-12, в каждом: Verdict / Evidence / Impact / Effort / Next
## Decomposition    — таблица: Item | Verdict | Next task | Why
## Constraints      — что нельзя трогать и почему
```

`Item` в таблице — ровно `CR-NN`, вердикт в таблице совпадает с вердиктом в секции `### CR-NN`. Язык отчёта — русский, имена файлов/символов/флагов дословно.

## Edge cases

- Артефакта нет (`CODING_STANDARDS.md`, `config/workspace.example.json`, `docs/setup.md`, `scripts/rt_browser_refresh.py`) → вердикт `open` или `needs-spec`, не `done`. Для `done` oracle требует существования файла.
- Пункт уже сделан и это видно в коде → `done` только с `path:line`. Пункт, который нельзя проверить чтением (нужен прогон живого конвейера, сеть, браузер) → `needs-spec` с причиной.
- CR-01: два скорера отвечают на разные вопросы — `score_candidate` в `rnext/planner.py` отбирает *исходное издание той же пластинки* (штрафы за live/vinyl/hi-res/alt-edition, порог 80), `score` в `scripts/tracker_hunt.py` ранжирует *качество издания* (lossless +100, источник, DR, логи). Механическая склейка ломает оба контракта; отчёт обязан зафиксировать это как два контракта и предложить вынос общей части (lossless/EDITION/media/`[TR24]`-классификация) в `rnext` с двумя тонкими обёртками вместо склейки функций.
- CR-12: SKILL.md-файлов много, в постановке не сказано какие два — воркер ищет по `git status`/`git log`, а если не нашёл, ставит `needs-spec`, а не угадывает.
- CR-06 распадается на две части (docs + скрипт) — это одна строка таблицы, `Next task` описывает обе.
- Секреты: в отчёт не попадают содержимое `.env`, cookies, `cf_clearance`, токены Transmission — только имена файлов.

## Risks

| id | риск | мера |
|---|---|---|
| R1 | воркер «заодно» правит код по найденным пунктам | `allowed_paths` = только файл отчёта; Forbidden в спеке |
| R2 | отчёт-заглушка, пересказывающий постановку | oracle: 12 секций, `path:line`, таблица, ≥3000 символов, запрет TODO/TBD |
| R3 | ложный `done` | oracle: для CR-05/06/08/10 `done` требует существования артефакта, иначе нужен `path:line` |
| R4 | расхождение выводов и таблицы | oracle: вердикт в `### CR-NN` == вердикт в `Decomposition` |
| R5 | задет живой конвейер | секция `Constraints` обязана перечислить три скрипта и `/media/mydum/Data`; Forbidden |
| R6 | утечка секретов в отчёт | Forbidden: только имена, без содержимого |

Риск задачи — low: единственная запись — новый markdown-файл, ничего исполняемого не меняется. Негативный корпус не нужен.

## Open questions

**CR-01 «объединить два скорера в один».** Буквальное прочтение (одна функция на оба случая) несовместимо с семантикой: `score_candidate` в `rnext/planner.py` выбирает *исходное издание той же пластинки*, `score` в `scripts/tracker_hunt.py` ранжирует *качество издания* для пользователя. Рекомендация: в отчёте зафиксировать два контракта, а «объединение» свести к выносу общей части (классификация lossless / EDITION / media / разбор `[TR24]`, `[CD]`, vinyl) в `rnext.release_quality` с двумя тонкими обёртками; сама правка — отдельная spec medium risk с oracle на записанных строках выдачи трекера. Нужно решение владельца: принимается ли такое прочтение или требуется буквально один вызов на оба случая.
