# PRD — eval: our per-track restoration vs. master restorations

Task: `t-20261104-235752-цель-оценить-насколько-наш-скил-7a46f8`
Source request: `requests/t-20261104-235752-цель-оценить-насколько-наш-скил-7a46f8.md` (untrusted data)

## Goal

Make the "ours vs. masters" comparison a reproducible, machine-checked procedure instead of an
ad-hoc series of manual measurements:

1. A seeded, deterministic selection of releases from the two master corpora
   (`5618698.jsonl`, `3048819.jsonl`): 5 per master, seed `20261104`, `seeds >= 3`, single albums
   preferred over discographies.
2. A neutral measurement of three sides per album — `ORIG` (the album as the master received it),
   `OURS` (our per-track restoration of `ORIG`), `MASTER` (the master's restoration) — reusing
   `scripts/audio_measure.py` metrics: `dr14`, crest, `lufs`, true peak, clipping, spikes > 0.9,
   band RMS spectrum.
3. Per-track and per-album closeness tables: `|OURS − MASTER|` against `|ORIG − MASTER|` as the
   baseline, plus a verdict `better | worse | comparable` per metric and overall.
4. A report at `docs/eval-vs-masters-2026-11-04.md` produced by the tool from the measured data,
   with the reproducible commands, and with every release explicitly marked `measured` or
   `skipped: <reason>` — no silent substitution, no hand-typed numbers.

The end state: one command reproduces the same selection, the same tables and the same verdict from
the same inputs; a reader can tell where our restoration is closer to the master than the original
was, and where it is not.

## Non-goals

- Changing restoration DSP, `scripts/restore_per_track.py`, `process_album.sh`, quality gates or any
  application code. The eval measures the skill as it is today.
- Improving our numbers. A verdict of `worse` is a valid, reportable outcome.
- Touching canons (`release/`), `~/Music`, the phone, `release_src` contents, or existing torrents
  outside the eval work area.
- A statistical study of the whole corpora (178 + 500 releases). The scope is 10 releases, and only
  those that can actually be fetched within the disk and seed constraints.
- Re-implementing DR/LUFS/spectrum math: `scripts/audio_measure.py` stays the single source of
  measurement.
- Publishing or uploading master restorations; they stay local for comparison.

## Use cases

1. **Coordinator wants the answer.** Runs the eval tool over a prepared manifest of 10 measured
   releases and reads the verdict block of the report: are we closer to the masters than the
   originals, on which metrics, and by how much.
2. **Reviewer questions a number.** Takes one row from `tracks.csv`, re-runs the pinned reproduce
   command for that release, gets the same value from `audio_measure.py`.
3. **Selection disputed.** Someone claims the sample was cherry-picked. The tool prints the picks for
   seed `20261104` byte-for-byte; re-running gives the identical list, and the selection is stored
   next to the data.
4. **A release dies mid-run.** Seeds are gone or the download never finishes: the release is recorded
   as `skipped` with the reason, the run continues with the next pick, the report states how many of
   the 10 were actually measured.
5. **Master has no local counterpart.** The master's restoration is not lossless / not fetchable: the
   album is skipped, not measured with a weaker substitute.

## UX

No new user-facing surface. The interaction is a CLI plus three files.

CLI (pinned flags; the worker may add more):

```
python3 scripts/eval_vs_masters.py \
    --manifest eval/manifest.json \
    --out-dir  eval/out \
    --report   eval/out/EVAL_REPORT.md
```

- `--manifest` — JSON `{"seed": 20261104, "releases": [{"release": str, "orig": path,
  "ours": path, "master": path}]}`. Paths are absolute or relative to the manifest's directory.
- `--out-dir` — where `tracks.csv`, `deltas.csv`, `albums.csv`, `summary.json` land.
- `--report` — optional markdown rendering of the same numbers.
- Selection mode:
  `--select --corpus <file.jsonl> [--corpus ...] --seed 20261104 --per-master 5 --out picks.json`.

Output contract (columns are the interface; extra columns allowed, these must be present):

| file | required columns |
|---|---|
| `tracks.csv` | `release, track, side, dr14, crest_db, lufs, true_peak_db, clip_samples, spikes_over_09` |
| `deltas.csv` | `release, track, metric, orig, ours, master, delta_ours_master, delta_orig_master, abs_delta_ours_master, abs_delta_orig_master` |
| `albums.csv` | `release, metric, orig, ours, master, abs_delta_ours_master, abs_delta_orig_master, verdict` |
| `summary.json` | `seed`, `releases[]` (`release`, `tracks`, `status`), `per_metric{metric: {abs_ours, abs_orig, verdict}}`, `verdict_overall` |

Rendered report (`docs/eval-vs-masters-2026-11-04.md`) keeps the headings `## Verdict`,
`## Per track`, `## Per album`, `## Reproduce`, and starts with the measured/skipped count.

Exit codes: `0` success, `2` bad input (missing side directory, unreadable jsonl, missing metric in
`audio_measure` output, `--select` without `--seed`). On `2` nothing is written to `--out-dir`.

## Edge cases

- Fewer eligible releases than `--per-master`: return all eligible, no error; `summary.json` and the
  report state the shortfall.
- `seeds < 3`, missing `seeds`, non-numeric `seeds`/`topic_id`: not eligible (missing/non-numeric →
  input error `2`, not a silent drop).
- Discography titles: preference, not a hard filter — if single albums run out, discographies fill the
  remainder.
- `ORIG` and `MASTER` have a different track count or names: match by track number (leading digits of
  the file stem); unmatched tracks are recorded as `skipped: track_mismatch` and excluded from album
  means, never zero-filled.
- A side directory is empty or has no decodable audio: exit `2`.
- `audio_measure.py` returns a missing/`null` metric for a file: exit `2`. No fallback, no `0.0`.
- `abs_delta_orig_master == 0` (original already equals the master): verdict is `comparable`, never a
  division by zero.
- Disk below 2 GiB free during the measurement run: stop and report, do not truncate the album set.
- Report regenerated from an existing `--out-dir` must not require re-downloading anything.

## Risks

1. **The eval run is network- and disk-bound, not code-bound.** 11 GiB free, `process_album.sh` needs
   ≥2500 MB RAM. Mitigation: one release at a time, temp under `restore/eval_tmp`, delete after
   measuring; the tool itself is testable offline against synthetic audio, so a failed download stage
   does not block the deliverable.
2. **Fabricated numbers.** A worker under pressure to produce a "good" verdict could type tables by
   hand. Mitigation: the report is rendered by the tool from the CSVs; oracle tests compare rendered
   report values with `summary.json`; the spec forbids hand-written metric cells.
3. **Selection cherry-picking.** Mitigation: seeded selection is a tested pure function with a pinned
   seed; the picks file is committed next to the result.
4. **Metric drift.** If `audio_measure.py` changes its schema, the eval breaks loudly (exit `2`)
   instead of silently comparing different things.
5. **Loudness mismatch misread as quality.** `OURS` is 4–6 LU quieter than the original by design;
   the report must present LUFS as a separate row and must not fold loudness into the "better" vote
   without saying so.
6. **Master restorations leaking into the collection.** Mitigation: `allowed_paths` excludes
   `release/`, `~/Music`, `release_src` mutation; the master side is read-only input.

## Verification plan

1. `python3 -m pytest oracle/t-20261104-235752-цель-оценить-насколько-наш-скил-7a46f8 -q` — the DoD
   command. Fails before the worker writes `scripts/eval_vs_masters.py`, passes after. Covers: metric
   normalization and physical sanity (a hard-clipped tone has lower DR/crest and more spikes than a
   quiet tone), verdict thresholds and tolerance, seeded selection determinism and `seeds >= 3`,
   single-album preference, shortfall, `--select` requiring an explicit seed, end-to-end CLI over a
   synthetic 3-side / 2-track album, loud failure on a missing side, rendered report headings and
   value consistency with `summary.json`.
2. Negative control: `oracle/negative/<ID>/kit.patch` injects three mutants into the pinned code
   blocks — inverted verdict comparison, ignored `seeds >= 3` filter, seed ignored in selection. Each
   must turn at least one oracle test red.
3. Manual, outside DoD (coordinator): the measurement run itself — picks file, 10 downloaded releases,
   the three sides actually measured, and the final `docs/eval-vs-masters-2026-11-04.md` with a
   non-zero measured count. A report with zero measured releases is a failed task, not a passing one.
